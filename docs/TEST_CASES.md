# 🧪 Project-MES 기능 검증 및 예외 상황 테스트 명세서 (Test Cases)

> **문서 목적:** `REQUIREMENTS.md`에 정의한 기능이 기대한 흐름으로 동작하는지 확인하기 위한 재현 가능한 테스트 절차를 정의합니다. 정상 흐름(Happy Path)뿐 아니라 입력값 오류, 권한 예외, 데이터 복구 및 반복 알림 등 주요 예외 상황을 포함합니다.  
> **중요:** 아래 테스트의 기본 상태는 `미실행`입니다. 테스트를 실제로 수행하고 근거를 확인하기 전에는 PASS로 변경하지 않습니다.

---

## 1. 테스트 상태 기록 기준

| 상태 | 의미 | 기록 기준 |
| :--- | :--- | :--- |
| 미실행 | 아직 테스트하지 않음 | 기본 상태 |
| PASS | 기대 결과를 확인함 | 실행 일시, 환경, 확인 근거를 함께 기록 |
| FAIL | 기대 결과와 실제 결과가 다름 | 재현 절차, 실제 결과, 오류 로그 또는 캡처 기록 |
| BLOCKED | 환경·계정·데이터·외부 API 문제로 실행할 수 없음 | 차단 사유와 재실행 조건 기록 |

> 코드에 기능이 존재한다는 사실은 테스트 PASS의 근거가 아닙니다. PASS는 브라우저 동작, API 응답, 화면 반영 또는 로그 등 실제 확인 결과를 기준으로 판단합니다.

## 2. 테스트 환경 및 사전 조건

### 2.1 기본 환경

- 프론트엔드 개발 서버와 백엔드 API 서버가 실행 가능한 상태
- 테스트 대상 브라우저에서 개발자 도구의 Console 및 Network 탭 확인 가능
- API 요청·응답과 인증 헤더를 확인할 수 있는 테스트 계정 준비
- 테스트 중 데이터 변경이 필요한 경우 개발용 데이터 또는 복구 가능한 테스트 데이터 사용

### 2.2 계정 및 테스트 데이터

| 데이터 | 준비 조건 | 사용 테스트 |
| :--- | :--- | :--- |
| 관리자 계정 | 정상 로그인 가능하며 관리자 역할 보유 | AUTH, PROC, HR |
| 일반 사원 계정 | 정상 로그인 가능하며 `EMPLOYEE` 역할 보유 | AUTH 권한 테스트 |
| 승인 대기 사용자 | 승인 대기 상태이며 승인·반려 가능한 데이터 | HR |
| 공정 라인 | 상태 변경 전후를 확인할 수 있는 라인 1개 이상 | PROC |
| 생산 실적 입력값 | 라인명, 목표량, 양품량, 불량량 입력 가능 | ANAL |
| PASS/FAIL 검사 이력 | 검색어와 판정 필터를 구분할 수 있는 검사 데이터 | QUAL |
| 설비 데이터 | 상태·온도·습도 값이 있는 설비, 상태 변경 가능한 테스트 설비 | EQP |
| 부품 데이터 | 현재 재고가 안전 재고보다 높은 품목과 낮은 품목 | SCM |
| 주소록 데이터 | 검색·필터·페이지 이동을 확인할 수 있도록 11명 이상 권장 | HR |
| 쪽지 계정 | 발신자와 수신자 각각 로그인 가능한 계정 | COM |
| 일정·공휴일 데이터 | 일정 CRUD가 가능한 월과 공휴일 API 조회 가능 환경 | COM |

## 4. 테스트 실행 기록

테스트 케이스의 상태를 PASS 또는 FAIL로 변경할 때 아래 실행 기록을 함께 작성합니다.

| Test ID | 실행 일시 | 테스트 환경 | 실제 결과 및 확인 근거 | 실행자 | 최종 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 예: TC-AUTH-01 | YYYY-MM-DD HH:mm | Local / Chrome | Network Authorization 헤더 및 로그인 후 화면 확인 | 이름 | 미실행 |

### 증적 기록 예시

- 화면: 테스트 전·후 화면 캡처
- API: 요청 URL, HTTP Status, Response Body
- 인증: 요청 헤더의 Bearer 토큰 포함 여부(토큰 원문은 문서에 기록하지 않음)
- 오류 처리: 사용자 안내 메시지, Console 오류 및 서버 로그
- 데이터: 테스트 전·후 목록 또는 상세 데이터 비교

## 5. 테스트 시 주의할 점

1. **인증 테스트:** 토큰 원문을 문서나 캡처에 노출하지 않습니다. 만료 테스트 후에는 정상 토큰으로 복구합니다.
2. **권한 테스트:** 프론트엔드 화면 차단과 백엔드 API 직접 호출 차단을 별도로 검증합니다.
3. **공정·인사 테스트:** 상태 변경 및 승인·반려는 데이터에 영향을 주므로 개발용 테스트 데이터로 수행합니다.
4. **폴링 테스트:** `MesAlertWatcher`의 주기는 15초이므로 상태 변경 직후가 아니라 다음 조회가 완료된 뒤 결과를 확인합니다.
5. **경보 중복 테스트:** `sessionStorage`의 `mes-alerted-keys` 기록이 이전 테스트에 영향을 줄 수 있으므로 테스트 시작 전 상태를 확인하고, 테스트 데이터·브라우저 세션을 분리합니다.
6. **클린룸 경보 테스트:** 온도·습도 숫자를 임의로 바꾸는 것만으로 경보가 발생한다고 가정하지 않습니다. 실제 감지 조건인 설비 `WARNING`·`ERROR` 상태를 변경해 검증합니다.
7. **주소록 테스트:** 현재 구현은 검색·필터·페이지네이션이며 행 가상화 성능 테스트로 해석하지 않습니다.
8. **외부 공휴일 API:** 외부 API 장애나 응답 지연이 발생하면 애플리케이션 오류와 외부 서비스 장애를 구분해 기록합니다.

## 6. 검증 범위의 한계

- 본 문서는 프론트엔드 화면과 API 연동 흐름을 중심으로 한 기능 테스트 시나리오입니다. 별도의 자동화 테스트 프레임워크를 이용한 단위·통합·E2E 테스트가 수행되었다는 의미는 아닙니다.
- 백엔드 트랜잭션, DB 정합성, 인증·인가 미들웨어는 연동 결과를 확인하는 범위이며, 백엔드 내부 구현 전체를 이 문서만으로 검증하지 않습니다.
- 성능 부하, 동시 사용자, 대규모 데이터 처리량, 보안 취약점 진단은 별도의 비기능 테스트 범위입니다.
- AI 모델 추론, WebSocket Push, 온·습도 임계치 직접 판정 및 주소록 행 가상화는 현재 확인된 구현 범위에 포함하지 않습니다.
